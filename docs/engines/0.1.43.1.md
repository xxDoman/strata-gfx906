## What it fixes / what it adds

Upstream 0.1.43.1 (2026-10-12, 33 commits) is a hotfix aimed at NVIDIA desktops, Windows, Intel and the
server. Three of its changes reach gfx906:

- `STRATA_ADAPT_OVERLAP` is **opt-in again on every machine** (#2010): the Linux-NVIDIA decode collapse
  two users hit on 0.1.43 (#1964) is fixed twice over. On HIP we were outside that regime anyway; on this
  box the engine prints `adaptive overlap: off: not on a layer split`.
- the prompt path is more forgiving: a loan larger than the auto chunk no longer ends the engine
  (#2090), and a request that finds the card nearly full says so, naming the `--vram-reserve-mib`
  that would leave room (#2065).
- the PLE/n-gram start-up check no longer switches to mmap by itself on a slow disk (#2040 — long
  prompts on a SATA SSD were about 7x slower).

On gfx906 the **decode path is unchanged** from 0.1.42: upstream's 0.1.43 speed work is gated to
gfx1200/gfx1201 and their source says so.

Three things in this image are ours:

1. **gfx906 rocBLAS solution table reader** (engine). Upstream PR #981 is closed and unmerged, and its
   gate (`STRATA_ENABLE_HIP`, the wave32 RDNA backend) never matches a gfx906 build, so the reader used
   to compile out silently. The image rebases it onto 0.1.43.1 **with the gfx906 gate inside the patch**
   and ships a table for this card (108 lines).
2. **Community benchmark's report header on AMD** (tools) — card names from the PCI id and the ROCm
   driver string read back; report header only, nothing in the measurement path. The one-line driver fix
   is proposed upstream as [#1974](https://github.com/Niko1221/Strata/pull/1974).
3. **Per-card VRAM reserve floor on a layer split** (configurator, [issue #1](https://github.com/xxDoman/strata-gfx906/issues/1)):
   later cards with no monitor keep 512 MiB instead of `0`; with `0` the first later stage could not fit
   its own verification arena (69 MiB at `--spec 3`).

## How that was proven

- **Sums:** the binary's sha256 is asserted **inside the build** (`Dockerfile:118`), so the image either
  contains exactly `c78456f3…` or does not build at all. `engine-version.txt` is checked at
  `Dockerfile:163-164`.
- **The hotfix cost us nothing** — same box, same config, same suite, 0.1.43.1 against 0.1.43:
  `16K prompt 543.9 -> 544.9 tok/s` (level, ranges overlap), `chat decode 41.2 -> 41.7` (level),
  `4K prompt 473.6 -> 460.7` (**-2.7%**, both ranges wide: 375-477 vs 404-471),
  `agent session decode 44.7 -> 43.4` (ranges overlap).
- **The table's own worth**, a toggle-on/off A/B on this engine (`--mmap-experts`, community run 4):
  **+19.7% at 4K and +24.2% at 16K prompt, first token 16-20% earlier, decode unmoved**.
- **The card-name patch** against the running engine, same config: `['Radeon Instinct MI50 32GB', 'AMD Radeon']`
  before, `['AMD Instinct MI50 32GB', 'AMD Radeon VII 16GB']` after; VRAM/driver/engine fields unchanged.

## What is NOT proven

- All of the above comes from **one box** (2x gfx906, MI50 32 GB + Radeon VII 16 GB) whose MI50 also has
  the UPP limit `TdcLimitGfx` at **150** — these are not stock-card numbers, and no third party has
  reproduced them.
- The **4K row lost 2.7%**; with ranges that wide the question is unresolved, not settled either way.
- The 16-bit prompt path the table uses changes prompt rounding (the engine says so itself: *not
  bit-identical to the default*); decode is unaffected. Quote the table as its own lever, never merged
  into one number.
- **No network pool** in this image: that lives only in the separate `0.1.40.1-pool` tag (a fork on
  engine 0.1.40).
- The upstream fixes listed above were **not** re-measured here beyond the A/B rows quoted.
