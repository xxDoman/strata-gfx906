## Two numbers, not one

Release `0.2.3`, engine **0.1.48** (0.2.2 shipped 0.1.47, 0.2.1 shipped 0.1.46). The image is tagged with the
release — the number on upstream's release page — and carries `release=0.2.3 / engine=0.1.48` in
`/opt/strata/RELEASE`, which is what the benchmark report reads.

## What upstream did with our reports — two of our patches are gone

Both fixes from our 0.1.45 line that used to be local are now upstream, so they are **not** applied any
more (re-applying them would duplicate code):

| our id | what upstream did |
|---|---|
| **E5a** — gate the NVFP4 W4A4 target out on gfx906 | #3172: that target now gets `GGML_USE_HIP` and builds. The gate would have removed a working target. |
| **E6** — `f16kq` link stub | #3271: gfx906 compiles `moe_f16_kq.cu` itself; on this arch it *is* the stub (`covers()` → false), so our extra file would duplicate symbols. |

What 0.2.3 itself brings, in the parts that touch this image: faster Strix Halo (`gfx1151`, not our card),
Intel Arc as a released engine package, the **DFlash2** drafter (opt-in, `strata launch --drafting dflash2`),
an agent chat that survives a full context, HTTPS that uses the **operating system's certificates**, new
defaults for CPU workers / VRAM / conversation-cache sizing, and a long list of Terminal and app fixes (a
second `strata launch` says "Already serving", `status`/`logs` work without an address, busy ports are named,
updates never cross GPU makes). **Nothing in the notes was measured on gfx906** — the release's numbers are
Strix Halo (Windows) and RTX-class cards.

## What we add on top

| id | what | why it is needed here |
|---|---|---|
| **E1** | attention score buffers sized from the model geometry (`n_head × tmax × ceil8(tmax)`), one slab of margin, warmup at 512 rows instead of the whole chunk | `q36_engine.cu` still sizes the buffer from a `64 << 20` constant; a chunk-sized batch fills it to its last element, which is the access fault the margin removes |
| **E2** | `ident`/`rinv` allocated with 128 ints of slack | the MMQ kernel reads `ids_dst[col_low + jt*J + j]` with `j < J ≤ 128` and masks only the store; here `ident` is a bare `cudaMalloc`, not a pool slice |
| **E3** | `upload_f32` accepts Q4_K (12) and Q6_K (14) via the tree's own `dequantize_q4_K`/`q6_K` | a Q4_K_M checkpoint leaves `ssm_alpha.weight`/`ssm_beta.weight` in the expert type and the loader aborts without it |
| **E4** | `X(12)` = Q4_K in `STRATA_D_FMTS`, both branches | upstream added `X(14)`/`X(146)` but not `X(12)`; without it `d_qk(12) == 0` and a Q4_K/Q4_K layer is refused |
| **E5b** | rocBLAS solution-table reader wired for gfx906 — `find_package(rocblas CONFIG QUIET)` in the `STRATA_HIP_GFX906` block and an `elseif(STRATA_HIP_GFX906 AND STRATA_ROCBLAS_AVAILABLE)` arm on `strata_prefill` | the reader is upstream, but its gate sits on `STRATA_ENABLE_HIP` while gfx906 takes the `HIP_GFX906` branch, so without the wiring it compiles to nothing **and still reports a clean build** |
| **E5c** | `cublasSgemm`, `cublasSgemmStridedBatched`, `cublasGemmStridedBatchedEx` → `hipblas*` in the **platform** compat header | only `cublasGemmEx` was mapped; the `qwen35moe` engine calls the others and the whole `strata` target fails to link |
| **E7** | `nextn_predict_layers` optional | upstream still requires the key; a Qwen3.6 file without the MTP block is a valid file and must load |
| — | the `qwen35moe` engine built for gfx906 (remove upstream's `if(NOT STRATA_HIP_GFX906)` around the family) | upstream keeps the family out of this build on purpose; we build and run it here |
| — | **DFlash2 build fix**: `cudaDeviceGetStreamPriorityRange` / `cudaStreamCreateWithPriority` → `hip*` | 0.1.48's new drafter calls both names and the wave64 compat layer mapped neither; without it the build stops on `dflash2.cpp` |

The **gfx906 rocBLAS table** (108 rows, tuned 2026-10-10 on MI50 against rocBLAS `5.2.0.dabb6df2b9`) travels
at `/opt/strata/rocblas-tuning.txt`, with `STRATA_ROCBLAS_TUNING` and `STRATA_HIP_PROMPT_F16=1` set in the
image. It is live on 0.1.48 — the engine logs `prefill gemm: rocBLAS tuning enabled (103 rows, 78 with a
solution, gfx906, rocBLAS 5.2.0.dabb6df2b9)`. Note the launcher points `STRATA_ROCBLAS_TUNING` at
`/opt/strata/tools/hip` (a directory) and the reader still finds the table, so both forms work.

The engine is a **portable build** (`STRATA_PORTABLE=ON`, one AVX2 baseline): `check_isa_guard` 0 violations
over 9 025 functions, 0 `vpdpbusd` in `ggml_vec_dot_q8_0_q8_0` (at `0x256ffe0`), and the `qemu-x86_64 -cpu
Haswell` probe runs with no SIGILL and a result identical to native (`-42.75`). MMQ is real code, not a stub:
`mmq::Context::run` = `0x36a`.

## What it is worth

Every row below was taken on **2026-10-23 at the factory power cap (MI50 225 W, Radeon VII 250 W)**, HTTP
`/v1/chat/completions`, a unique prompt (zero conversation-cache reuse), 128 output tokens, with the speed
read from the engine's own accounting — not from the client's clock. Rows at 80 W elsewhere in this repo are
**not** comparable with these: the cap is different by nearly 3×.

| model (quant) | prompt tok | prompt tok/s | decode tok/s | regime |
|---|---|---|---|---|
| Qwen3.8-Flash-Next-Uncensored **IQ2_XXS** | 32 319 | **702** | **46.0** | pack + `--mmap-experts --resident-budget-gib`, 99.8 % expert-cache hit, 0 file reads |
| Qwen3.8-Flash-Next-Uncensored **Q4_K_M** | 35 930 | 323 | 33.8 | resident complement 40.9 GiB, 92.5 % hit, 0.9 % of experts over PCIe |
| Qwen3.8-Flash-Next-Uncensored **IQ3_XXS** | 1 564 | 293 | 36.7 | resident complement 14.3 GiB, 98.9 % hit — no 32K point for this quant yet |
| **Ornith-1.5-35B-A3B Q4_K_M** (`qwen35moe`) | 2 229 | 1 026 | 68.0 | two rounds, spread < 0.4 % |
| **Ornith-1.5-35B-A3B Q4_K_M** (`qwen35moe`) | 8 744 | 993 | 56.0 | same run |

**The resident budget is what moves decode, not the new tag.** The same 35 930-token request on this very
image, before the expert complement was pinned in RAM, read **652 GB from storage** in one request and gave
148 tok/s prompt / 13.4 decode; with `--resident-budget-gib` it gave 323 / 33.8 and no file reads. The engine
pins only the **complement of the GPU cache** — the number in its log (`resident RAM: X GiB of experts`) is
that complement, not the budget you typed, which is why the 50 GiB setting showed up as 14.3 GiB on IQ3_XXS
(the cards were already full) and 40.9 GiB on Q4_K_M.

The rocBLAS table covers the dense prompt GEMMs (`f16_inplace`), so **decode cannot move** from it — experts
go through MMQ. The `q36` path does not log expert-cache or PCIe counters at all, so those two dashboard
columns stay empty for Qwen3.6/Ornith by design, not by a fault.

## What is not proven

- **No measurements at 80 W on 0.1.48.** The 80 W book rows (IQ2_XXS pack: 246–253 clean, 275–276 with the
  FP16 prompt path, 308–310 with the table) were taken on 0.1.46 and must not be compared with the rows above.
- **The table's rows are still not bit-identical** to the default path: `STRATA_HIP_PROMPT_F16=1` rounds each
  16-bit GEMM's output to FP16. No identity gate (KL/bitwise) has been run on 0.1.48 either.
- **DFlash2 has not been run as a drafter on gfx906.** It compiles (that is what the two CUDA name mappings
  bought); whether it wins on this card is unmeasured, and `auto` still means MTP.
- **Ornith is the only `qwen35moe` file run on 0.1.48.** Qwen3.6-35B-A3B-UD-Q6_K was not started on this tag.
- Speeds depend on where the experts live. Rows with `--mmap-experts` and no resident budget are disk-bound
  on this machine and say nothing about the engine's own ceiling.

## Running it

```bash
docker run -d --name strata \
  --device /dev/kfd --device /dev/dri \
  -v /path/to/models:/models -v /path/to/data:/data -v /path/to/work:/work \
  -p 8085:8085 -p 8090:8090 \
  xxdoman/strata-mi50:0.2.3
```

Engine on `:8085`, configurator on `:8090`. The image has an `ENTRYPOINT`, so `docker run <image> <cmd>`
starts the launcher — use `--entrypoint` for a probe.
