## What it is

Upstream **v0.1.45** brings Qwen3.6-35B-A3B reading images, `--parallel` up to 8 slots, new decode kernels and
a bigger default prompt chunk (4096/2048/1024 by free VRAM). On gfx906 it does not build or run without our
seven patches:

| id | what it fixes | why it is needed on gfx906 |
|---|---|---|
| **E1** | attention score buffers sized from the model's geometry (`size_att`), batch slab keeps one row-of-every-head of margin, warmup of 512 rows | the fixed `kAttScoreFloats = 64 << 20` is exactly 16 heads × 2048 rows × 2048; with 0.1.45's default chunk of 4096 it is 4× too small |
| **E2** | 128 ints of slack for `ident` / `rinv` | the MMQ kernel reads `ids_dst[col_low + jt*J + j]` with `J ≤ 128` past the rows and masks only the store |
| **E3** | `upload_f32` accepts Q4_K / Q6_K | a Q4_K_M qwen35moe file keeps `ssm_alpha` / `ssm_beta` in the expert type — 0.1.45 takes only F32/BF16/F16/Q8_0 there |
| **E4** | `X(12)` (Q4_K) in `STRATA_D_FMTS` | without it `d_qk(12) == 0` and a Q4_K/Q4_K layer is refused with a message that blames the Q6_K flag |
| **E5** | CMake: the Blackwell-only NVFP4 W4A4 unit is gated out on gfx906; the rocBLAS table reader is wired for gfx906 by hand; `cublasSgemm*` shims in the platform compat header | the W4A4 TU pulls `ggml-cuda/vendors/cuda.h` (a HIP build cannot include it); the reader's own detection sits in `cmake/hip_backend.cmake`, which this build never enters |
| **E6** | a `f16kq` stub (`covers()` / `covers_down()` false) | `moe_f16_kq.cu` is gfx11 WMMA code compiled only by the wave32 branch, while `moe_fused_iq.cu` calls its four entry points unguarded → `undefined symbol` at link |
| **E7** | `qwen35moe.nextn_predict_layers` optional | 0.1.45 requires it again; a Qwen3.6 file without an MTP block is a **valid** file (only the draft path needs it) and was unloadable otherwise (`missing qwen35moe.nextn_predict_layers`) |

Two patches of the 0.1.44.1 line were **absorbed upstream** and are not re-applied: the geometry guard for an
all-zero `compress_ratios` (#2396) and the rocBLAS table reader itself (our PR #981).

## What it is worth (measured here, 80 W cap on the MI50, medians of 3, `--tg 128`)

| model / path | prefill tok/s at 2K / 8K / 16K | decode tok/s |
|---|---|---|
| Ornith-1.5-35B-A3B Q4_K_M, `q36`, one card | 697 / 637 / 580 | 54.7 / 54.5 / 54.0 |
| Qwen3.6-35B-A3B Q6_K, `q36`, one card | 574 / 552 / 507 | 53.2 / 53.9 / 53.1 |
| Qwen3.8-Flash-Next IQ2_XXS, pack path, both cards, low-RAM off, kv q4_0 | 356 / 447 / 465 | 38.7 / 35.9 / 35.9 |

Head to head with 0.1.44.1 on the same configuration and cap: on the `q36` path **+15 % decode** at
**−8…−10 % prefill** (clean separation, TG 46.2–46.9 → 53.1–53.9); on the pack path **no difference**
(prefill within 0.6 %, decode inside its own scatter).

## How it was proven, and what was not

- Build: `BUILD=0`, no `error:`/`FAILED:`, `GLIBC_2.38`, `mmq::Context::run` real code (`0x2fa`), rocBLAS
  reader strings present.
- Portability: `STRATA_PORTABLE=ON` — the ISA guard reports 0 violations, `ggml_vec_dot_q8_0_q8_0` carries
  0 `vpdpbusd`, and the qemu `-cpu Haswell` probe runs without SIGILL and returns the same value.
- Release gate: page HTTP 200, model scan 14 models with 0 `Traceback`, tags in the registry equal to the
  release record.
- **Not proven:** token-for-token equality against 0.1.44.1 (the `+15 %` decode is a time measurement, not a
  proof of the same text), and the release gate's GPU point (loading a pack and generating a token) was not
  run on this build before publishing.

## Not in this build

- The **int8 KV cache on the `q36` path** (that was the 0.1.44.1 line, binarka `cb4d99d5`). 0.1.45 rewrote the
  attention path, so it needs its own port and its own A/B.
- The `--parallel` and image switches in the **configurator** — the engine and the server have them, the form
  does not expose them.
