## What it fixes / what it adds

- **`Models Infos` panel** (Configuration → `#miover` / `#b_mi`) with four sections that classify every
  GGUF found on the host: *native* (the engine takes it as-is), *our engine patches needed but the file
  is fine*, *bad metadata* (`compress_ratios` all zeros / missing MTP key), *completely incompatible* —
  each row with a machine-readable reason code.
- **Metadata repair on header copies**: `attention.compress_ratios` and `nextn_predict_layers` are fixed
  in place on a copy of the header, never by rewriting the model.
- **Start gate**: `POST /api/start` refuses to spawn the engine for a model whose verdict is `bad`, and
  shows the verdict's own wording (e.g. `general.architecture = 'llama'` — the engine only knows
  `qwen4exp` and `qwen35moe`) instead of the engine dying later with `unknown argument`.
- The engine itself is new to this repository's image line: upstream **v0.1.44.1 + 11 of our patches**.

## How it was proven

- `docker build -f Dockerfile.144-1b` passed **every** `RUN` control: engine sha256 match, rocBLAS table
  108 lines, MMQ real code (`0x26e`, not a stub), launcher `py_compile` + panel/version anchors,
  `engine=0.1.44.1`.
- Smoke test in a **separate** container (`strata-0441b-smoke`, ports 8100/8199, card 2, own copy of the
  config): `/api/status` answered, the image reported `engine=0.1.44.1` and the engine binary sha
  `9859791a`, the panel returned the four sections with counters **3 / 1 / 2 / 8** (identical to the
  earlier record), `POST /api/start` on nine `bad` models returned `blocked: true` with the verdict's
  reason and **no** `unknown argument`, and the config was neither written nor the engine spawned.
- The header repair was proven end-to-end **on a full 44 GB copy**: 48 bytes changed, header and tensor
  directory untouched, the geometry gate went `geo_odpuszczone` → `ok`, the original file's sha256
  unchanged.
- `git apply --check` of the whole patch set on a clean `v0.1.44.1` tree: 10 of 11 clean, `GFX906-5`
  rebased with `--fuzz=2` and the resulting file byte-identical to the 0.1.44 tree (only upstream's
  `f16_to_f32` differs).

## What is NOT proven

- **No no-regression run** (step 2 of the round) — there was no free VRAM (`card2` held by the
  production container, `card1` forbidden). **PP/TG numbers for this binary were not measured in that
  round** and are deliberately absent from it. (They were measured later *on the same binary* through the
  `q36` path and ingested into the benchmark ledger: PP/TG medians 618.1 / 66.1 tok/s default, 490.1 /
  60.8 with the production 192/256 split, 180 W, MI50 alone at `ctx 8192` — **a different path and
  regime** than the packed model this image ships for.)
- **The engine actually starting a model from this image** — it was attempted and died on VRAM; the panel
  and the Start gate were tested, the engine start was not.
- `--chunk 2048` / `4096` on the new binary were **not run**: the binary carries the same `ENG-2` fix as
  `d037f2bd`, so `EXIT=0` would be an expectation, not a measurement.
- `GFX906-5` behaviour after the `--fuzz=2` rebase — **not measured on a live GPU**.
- Upstream 0.1.44.1 changes outside our scope (`serve/`, `setup.py`, `tools/`, `metal/`) — untested, and
  not ours.
- The `compress_ratios`-all-zeros defect in the production model files stays open: the configurator can
  repair them, the production file was not touched (only a copy).
- The tag was **never published**, so there is no external reproduction of any of this.
